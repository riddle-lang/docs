# 引用与逃逸

引用让你在不移动值的情况下临时访问它。
Riddle 的引用模型和内存分配策略紧密相关：如果引用没有逃逸当前作用域，值可以留在栈上；如果引用逃逸，整个变量会自动提升到 GC 管理区域。

## 临时引用

临时引用最常见的用途是把值借给函数使用：

```riddle
struct Foo {
    x: i32,
    y: i32,
}

fun print_foo(foo: &Foo) {
    print(foo.x)
}

fun main() {
    let foo = Foo { x: 1, y: 1 };
    print_foo(&foo);
    print(foo)
}
```

`&foo` 没有逃出 `main` 的当前作用域。调用结束后，`foo` 仍然可以继续使用。

## 引用逃逸

如果引用离开了当前作用域，它就发生了逃逸。
常见的逃逸包括：

- 从函数返回引用；
- 把引用存进生命周期更长的数据结构；
- 让闭包或异步任务捕获引用；
- 把引用传给可能保存它的外部接口。

当逃逸发生时，Riddle 不要求你手动选择堆分配或写生命周期标注。
编译器会把整个变量提升到 GC 管理区域。

## 自动提升到 GC

看一个概念示例：

```riddle
fun make_ref() -> &Foo {
    let foo = Foo { x: 1, y: 1 };
    &foo
}
```

`foo` 的引用被返回了。它不能再只存在于 `make_ref` 的栈帧中。
因此 Riddle 会把整个 `foo` 提升到 GC 管理区域，让返回的引用保持有效。

这和 Go 的逃逸分析有相似之处：程序员通常不需要手动决定一个对象放在栈上还是堆上。
不同的是，Riddle 的普通值语义仍然以移动为核心。

## 提升后变成引用语义

一旦变量被提升到 GC，它会自动变成引用语义。
这意味着多个地方可以持有指向同一个 GC 对象的引用，而对象的存活由 GC 管理。

```riddle
fun main() {
    let foo = Foo { x: 1, y: 1 };
    let a = &foo;
    let b = a;
    print(b.x)
}
```

如果 `a` 或 `b` 的使用方式导致引用逃逸，`foo` 会被提升。
提升之后，围绕这个对象的访问更接近引用语义，而不是普通栈上值的移动语义。

## 为什么这样设计

Rust 要求程序员显式面对借用和生命周期，这能换来非常强的静态保证，但学习成本很高。
Go 让编译器做逃逸分析，程序员写起来轻松，但值的归属感没有那么强。

Riddle 尝试结合两边的优点：

- 普通值用移动语义保持清晰归属；
- 临时引用保持轻量；
- 逃逸时自动提升，不要求手写生命周期；
- 提升后交给 GC 管理，避免悬垂引用。

## 逃逸分析详解

以下是 Riddle 逃逸分析的完整规则。日常编码不需要刻意记忆这些——编译器会在逃逸发生时自动处理。

### 核心规则

1. **局部性原则**：变量默认在栈上分配，所有权规则不变。
2. **逃逸检测**：当编译器检测到某个变量的引用被传递到其声明的词法作用域之外时，触发逃逸标记。
3. **自动提升**：逃逸的变量自动从栈迁移到 GC 管理的内存区域，其生命周期由 GC 控制。
4. **零开销回退**：若逃逸分析判定引用未逃逸，则依然享受栈分配的高性能和确定性的析构。
5. **跨函数逃逸**：引用作为返回值或通过闭包捕获时，同样触发逃逸分析，对涉及的所有变量进行 GC 提升。

> 分析粒度为**整个变量**（StmtId），不做字段级拆分。

### 触发逃逸的场景

#### 引用作为函数返回值

当一个局部变量的引用通过 `return` 流出函数时，该变量逃逸：

```riddle
// s 逃逸 —— 引用被返回
fun dangling() -> &Foo {
    let s = Foo { x: 42 };
    return &s;
}
```

```riddle
// s 不逃逸 —— 引用仅在函数内使用
fun no_escape() {
    let s = Foo { x: 42 };
    let r = &s;
    print(r.x);
}
```

#### 引用赋值给外层变量

当局部变量的引用被写入到比当前函数存活得更久的存储位置时，该变量逃逸：

```riddle
var GLOBAL: &Foo;

fun store() {
    let s = Foo { x: 42 };
    GLOBAL = &s;   // s 逃逸
}

fun via_param(container: &mut &Foo) {
    let s = Foo { x: 42 };
    *container = &s;  // s 逃逸：写入参数指向的外部位置
}
```

#### 引用作为函数参数传递

当一个局部变量的引用被传给其他函数时，编译器采用保守策略，标记为逃逸：

```riddle
fun take(p: &Point) { /* 函数体不在当前编译单元可见 */ }

fun caller() {
    let s = Point { x: 1, y: 2 };
    take(&s);  // s 逃逸：&s 传入了外部函数
}
```

> 例外：如果被调用函数在当前编译单元内且编译器确认其不保存引用（如纯读取），可以不触发逃逸。这部分依赖过程间分析。

#### 结构体或数组包含引用后逃逸

当一个包含引用的聚合值自身逃逸时，其内部引用指向的变量也受牵连逃逸：

```riddle
struct Pair {
    val: &Point,
}

fun build() -> Pair {
    let s = Point { x: 1, y: 2 };
    let p = Pair { val: &s };
    return p;  // p 逃逸 → p.val 引用逃逸 → s 逃逸
}
```

```riddle
fun array_escape() -> &Point {
    let arr = [
        Point { x: 1, y: 2 },
        Point { x: 3, y: 4 },
    ];
    return &arr[1];  // arr[1] 逃逸 → 整个 arr 逃逸
}
```

#### 闭包捕获

当闭包捕获了局部变量的引用，且闭包自身逃逸到外部时，被捕获的变量逃逸：

```riddle
fun make_counter() -> fun() -> i32 {
    let count = 0;
    return fun() -> i32 {
        count = count + 1;
        return count;
    };
    // count 被闭包捕获且闭包逃逸 → count 逃逸
}
```

#### 条件分支中任一分支逃逸

在 `if` / `match` 等控制流中，只要有一个分支导致变量逃逸，该变量即在所有路径上被视为逃逸：

```riddle
fun maybe_leak(flag: bool) -> &Point {
    let a = Point { x: 1, y: 2 };
    let b = Point { x: 3, y: 4 };

    if flag {
        return &a;  // a 逃逸
    } else {
        return &b;  // b 逃逸
    }
    // 结果：a 和 b 都逃逸
}
```

#### 循环中取引用并逃逸

```riddle
fun in_loop() -> &Point {
    loop {
        let s = Point { x: 1, y: 2 };
        return &s;  // s 逃逸
    }
}
```

### 不触发逃逸的场景

以下场景虽然取了引用，但引用没有流出当前作用域，变量留在栈上：

```riddle
// OK：引用仅在函数内使用
fun ok() {
    let s = Foo { x: 42 };
    let r = &s;
    let val = r.x;
    print(val);
    // s 不逃逸，留在栈
}

// OK：Copy 类型的引用不影响分配策略
fun copy_type() {
    let x: i32 = 42;
    let r = &x;
    print(r);
}

// OK：引用作为函数参数，但函数是纯读取
fun helper(p: &Point) -> i32 {
    return p.x;
}

fun caller() {
    let s = Point { x: 1, y: 2 };
    let v = helper(&s);
    // 如果编译器确认 helper 不保存 &s，s 可以不逃逸
}
```

### 逃逸分析算法

编译器采用两遍扫描加不动点迭代的方式：

1. **第一遍（自底向上标记）**：遍历函数体中的每个表达式，判断其是否产生"包含对局部变量引用"的值，并将这些值向上传播。

2. **第二遍（传播到被引用变量）**：如果某个表达式被标记为逃逸，找到它引用的局部变量（`&x` 中的 `x`），将该变量标记为逃逸。如果该变量自身也被引用，递归传播。

由于变量之间可能存在引用链（`&a` 引用了 `b`，`b` 又引用了 `c`），逃逸标记需要不动点迭代直到稳定。

### GC 内存管理

逃逸分析与 GC 的配合方式：

| 逃逸分析结果 | 分配位置 | 生命周期管理 |
|------------|---------|------------|
| 未逃逸 | 栈 | 函数返回时自动释放 |
| 已逃逸 | GC 堆 | 由 GC 追踪可达性，不再可达时回收 |

栈与堆的交互 —— 逃逸的变量在 GC 堆上分配后，栈上只保留一个指向堆的胖指针，所有对该变量的访问通过该指针间接完成：

```
栈                              GC 堆
┌──────────────┐               ┌──────────────────┐
│ s: *Point ───┼──────────────→│ Point { x:1 y:2 }│
└──────────────┘               └──────────────────┘
```

GC 特性：
- 每次堆分配前检查阈值，超出时触发 GC
- 支持并发标记以减少 STW（Stop-The-World）时间
- 非移动式 GC：对象地址不变，指针无需更新，与 FFI 交互时指针保持稳定

### 未来扩展

- **字段级逃逸**：仅将逃逸的结构体字段提升到堆，其余字段保留在栈
- **过程间分析**：跨函数跟踪引用的生命周期以消除保守的逃逸标记
- **栈上分配优化**：对短暂逃逸的对象使用栈分配 + 引用计数混合方案

## 小结

- 引用用于临时访问值；
- 引用不逃逸时，值可以留在栈上；
- 引用逃逸时，整个变量自动提升到 GC；
- 提升后对象变成引用语义；
- 这个模型借鉴 Go 的逃逸分析，同时保留 Riddle 的移动语义；
- 编译器自动处理逃逸分析，日常编码不需要手动干预。
