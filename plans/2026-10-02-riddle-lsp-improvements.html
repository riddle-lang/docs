Riddle 语言服务器 · 审计日期 2026-10-02 · 基线 3a783d1 (app/riddle-lsp, 24 个源文件, ~8.5k 行)

北极星：让 riddle-lsp 在一万余行的 Clue 多包项目里做到「输入不掉帧、诊断不撒谎、重构不用手」。 当前服务器功能面已经相当完整（47 个 LSP 方法、29 项能力、1300 行协议级冒烟测试）， 真正的短板集中在三处：一份增量修改触发多次全项目分析、 两处会静默骗过用户的同步/编码缺陷、 能力声明与实现不一致导致编辑器不显示已有的功能。 因此本规划的前两期不新增功能，只修正确性与延迟；功能扩展排在第三期之后。

1 · 范围、非目标与授权边界

范围内

  • app/riddle-lsp 全量源码；只读依赖 app/clue、app/riddlec、crates/syntax 的接口。
  • 四个编辑器适配：editors/vscode、editors/zed、editors/helix、editors/intellij。
  • 协议级测试 editors/lsp-smoke.mjs 与 CI 接入方式。

非目标

  • 不改动编译器前端/类型检查/move checker 的语义与诊断集合（除「新增未使用导入诊断」这一项，见 WS-5）。
  • 不引入新 crate 依赖（性能修复全部用标准库 + 现有 tokio/tower-lsp）。
  • 不做 extract function 这类需要重写代码块的重构；只做基于现有索引可安全生成的种类。
  • 不为中文标识符增加词法支持（见下方前提更正）。

前提更正（影响 WS-5 的优先级判断）。Riddle 目前不是中文标识符语言： 词法只接受 ASCII，#[regex(r"[a-zA-Z][a-zA-Z0-9_]*")]（crates/syntax/src/lib.rs:168-170）， std/*.rid 中无 CJK。所谓「中文语言」指中文文档与中文优先的教学材料。 重命名走词法校验，因此中文新名会被拒绝（app/riddle-lsp/src/navigation.rs:1316-1324）。 反讽的是 LSP 侧的标识符扫描器是 Unicode 感知的（text.rs:103-105 用 char::is_alphanumeric）， 于是补全/语义 Token 的边界比词法更宽——这条「准备好了但用不上」的路径不应被当作已完成能力对外宣传。

假设与未知

  • 实测已补齐（2026-10-02 更新）。WS-0 的观测点已落地：--trace-latency / RIDDLE_LSP_TRACE_LATENCY（LSP 侧每个相位）、RIDDLEC_PHASE_TIMING（编译器流水线 1 parse / 2 lower HIR / 3 scope graph / 4 type check / 5 escape / 6 move-borrow），以及 cargo bench --bench lsp_completion。实测推翻了两条推断：
    • 补全本身不慢：修掉重复分析后只有 4–20 ms。编辑器感到的等待是 诊断那趟 Check 分析占着 CPU，补全在排队。
    • 那趟分析约 900 ms 里，4 type check 独占 660–1000 ms （parse 7 ms、lower HIR 32 ms、scope graph 30 ms、escape 59 ms、move/borrow 36 ms）。
  • 仍未解决，但机制已定位。标准库在打字期间不变，IncrementalTypeChecker 也确实能复用——命中时 827 个函数体全部复用、耗时 15–22 ms，相位计数器打印 [checked 0, reused 828]。但多数按键打印 [checked 827, reused 0]。 失败分类（absent = 检查器里根本没有条目，missed_context = 条目在但上下文指纹变了）。 已解决，根因与修复如下：
    • 根因：类型引用把源码位置当成了类型标识。 HirTypeRef 与 HirAssocTypeConstraint 是 #[derive(PartialEq, Eq, Hash)]，而 impl Trait / dyn Trait 变体带 trait_range: TextRange、关联类型约束带 range，于是被一起哈希。 管线把用户代码拼在标准库之前（format!("{source}\n\n{std}")）， 所以用户改一个字符就让 std 的每个 impl Trait 平移，类型上下文指纹随之变化， 827 个 std 函数体全部作废——尽管 std 一个字都没改。 实测受影响的正是 20 个接受 fun 参数的高阶函数 （or_insert_with/fold/map/and_then…）， 它们的签名里含 impl Trait。 HirPath 早已手写 Hash 排除自己的 range，这两处漏了。
    • 修复：手写 PartialEq/Hash，按语义而非位置比较类型。 与 HirPath 保持一致。类型标识不再随周边源码长度漂移。
    • 效果：一次按键只重检被改的那 1 个函数体。 相位计数从 [checked 827, reused 0]（约 688 ms）变为 [checked 1, reused 826]（约 17 ms），globals_rebuilt false。 tests/clue/project_session.rs::a_one_character_edit_rechecks_only_the_edited_body 钉住了这条：真实项目里改一个字符后 checked_bodies == 1、 missed_context == 0、missed_body == 1。
    同一轮还顺带修掉三处：IncrementalParser::set_source 不再对相同文本 无条件 parse_full（语言服务器每次请求都传入完全相同的 ~240 KB bundle）； 两套 AnalysisSessions 合并为一（原先 analysis_sessions 与 completion_sessions 各自从零构建 std）； type_context_fingerprint_with_ranges 不再哈希 format!("{tree:?}")。
  • 剩余（已量化）：冷启动。改造后 36 次整项目检查里， 21 次是各检查器的首次填充（缓存为空，必须建 std 的 827 条）， 热态却全量重检只剩 1 次。也就是说单文档连续打字已经是最优路径 （missed_body 1），剩下的是每个新文档/项目的首帧代价： 冒烟测试的 first member 约 850–900 ms、cargo bench 的 cold 约 820–1040 ms。补全自身为 4.4 / 9.0 / 19.2 ms（1/8/24 模块）， 但在首个请求时仍要排在那一趟 Check 分析之后。 若继续优化，方向是让 std 的检查结果能跨会话复用（进程级共享），而不是每个 CheckSession 各建一份。
  • tower-lsp 0.20.0 的调度语义已核实：请求以 buffer_unordered(4) 在单个驱动任务内轮询 （transport.rs:22-23,116-142），队列容量 MESSAGE_QUEUE_SIZE = 100； $/cancelRequest 由 Cancellable 层用 future::abortable 实现， 因此只能中断响应、无法停止 spawn_blocking 线程。
  • 未核实：Riddle 是否有颜色字面量（决定 documentColor 是否有意义）； declaration 与 definition 是否存在语义差别（当前二者互为转发）。

4 · 推荐路径与备选方案

推荐：先证据、再止血、后扩展

WS-0 → WS-1 与 WS-2 并行 → WS-3 → WS-4/WS-5/WS-6 并行 → WS-7 收尾。 理由：WS-1 与 WS-2 都在改 server.rs 的请求路径与状态机，先合并会持续冲突； 而 WS-1 的「不同步」状态本身就是 WS-2 需要的取消/失效信号源，因此 WS-1 先落地成本更低。

WS-0 · 观测先行 顺序：第一步

在动任何性能代码之前，先让延迟可测量。当前 crate 无一处计时，任何优化都无法证明有效。

  • 加 5 个计时点并通过 $/logTrace 或 window/logMessage（DEBUG 级，可由 CLI 开关控制）输出： did_change→publishDiagnostics、ProjectSession::load、流水线深度、spawn_blocking 等待时长、处理器总时长。
  • 加一个 riddle-lsp --trace-latency 开关，默认关闭，避免污染正常日志。

验收：同一份万行项目下，能打印出每次按键的上述 5 个数字；无开关时零额外开销（不分配、不格式化）。

WS-1 · 正确性与同步 阻断级

1.1 无法映射的增量修改会导致诊断静默变空（最高优先级）

证据链（已逐步复核）。 apply_content_changes 对任何不可映射位置直接返回 false，不做钳制、不做部分应用（app/riddle-lsp/src/text.rs:53-76）； did_change 收到 false 后把该 URI 从 docs 中移除、提升相关修订号、直接 return， 全程没有调用 schedule_diagnostics()（app/riddle-lsp/src/server.rs:413-429）。 随后任意其他文件的变化触发一次收集，该 URI 已不在 docs 中， 于是 publish_diagnostics 按 previous ∪ current 的键集合为它推送空数组加过期版本号（server.rs:1897-1917）。 pull 路径同样返回空报告，且 .unwrap_or_default() 还会把 panic 也变成「干净」（server.rs:551-570）。

触发条件（任一即可）：行内存在星光面字符（emoji）并被增量区间跨越；客户端发来超出行长的列号； 区间起止落在代理对中间——后者正是 text.rs:96-98 主动拒绝的情形。

复现要点：源码 let x = 1; // 😀，用增量 range 删除该 emoji。 代码注释里写的恢复路径（server.rs:390-409）只在无 range 的全量替换下生效， 而服务器声明的是 INCREMENTAL 同步（server.rs:193-195），合规客户端永远不会发全量替换。

目标行为：任何无法映射的修改都不得渲染为「无问题」。

  • 首选：对位置做钳制（列号夹到行长、区间夹到文档范围、代理对中间向下取整到字符边界）， 仅当结构性不一致（如 range 长度与文本长度矛盾到无法解释）时才判定不同步。
  • 必须保留兜底：设一个 per-URI 的 out_of_sync 标记； push 时对该文件推送一条 Error 级诊断说明「编辑器与服务器状态不一致，请重新打开该文件」； pull 时返回 DocumentDiagnosticReport::Unchanged 或 JSON-RPC 错误，绝不返回空集。
  • 把 server.rs:569 的 .unwrap_or_default() 换成显式错误上报，避免 panic 伪装成「无问题」。

1.2 positionEncoding 只声明不协商

position_encoding: Some(PositionEncodingKind::UTF16) 是无条件硬编码（server.rs:192）， initialize 只读取 watched-files 与 type-hierarchy 两项客户端能力，从不读 general.positionEncodings（server.rs:255-309）； 全部位置换算也硬编码 UTF-16（text.rs:35-38、text.rs:89-100）。 VS Code 默认即 UTF-16 且会回显服务器选择，因此不受影响；风险在只支持 UTF-8/UTF-32 的客户端——它们会逐行偏移， 而偏移又会反过来触发 1.1。

目标：读取客户端 general.positionEncodings，按「UTF-16 > UTF-8 > 首个交集」协商，并把选中的编码贯穿 LineIndex 与 offset_for_position。若只做一件事，至少要在客户端列表不含 UTF-16 时拒绝启动并明确报错，而不是默默用错编码。

1.3 重命名对非法目标返回裸 null，且与 prepareRename 判定不一致

navigation.rs:1161-1162（symbol_at(...)?.definition?）与 navigation.rs:1144-1145（target.binding.as_ref()?） 在目标不可重命名时返回 None，最终变成 server.rs:1421 的 Ok(None) → JSON null。 而 prepare_rename_from_analysis（navigation.rs:1113-1123）与 rename_from_analysis 用了不同的守卫， 于是存在「prepare 接受了、rename 却返回 null」的目标。VS Code 对 null 不显示任何错误，用户只会觉得重命名没反应。

目标：不可重命名时返回 invalid_params 并给出原因文案；抽出同一个守卫函数供 prepare 与 rename 共用。

1.4 pull 诊断的细节

  • 从不产出 resultId（full_diagnostic_report，server.rs:1862-1872），related_documents 恒为 None。 前者使客户端无法做增量确认；后者可直接由 diagnostics.rs:517-540 已经构建好的跨文件 relatedInformation 推导。
  • diagnostic_provider 无条件声明（server.rs:229-234），且声称 inter_file_dependencies: true 却把 workspace_diagnostics 设为 false。
  • pull 处理器传入硬编码的 || false（server.rs:559），即完全不可取消， 并且在整个工作区分析期间持有 diagnostic_sessions 互斥锁（server.rs:556-558），使并发的 pull 与 push 流水线全部排队。 这条与 WS-2 的取消机制同源，实现时应一并处理。

1.5 次要项

  • did_change 不校验版本单调性（server.rs:431，对比 did_open 的 :375-378）。
  • rangeLength 被忽略（text.rs:58-73）——可用来交叉验证客户端区间。
  • 未知文档且批次内无全量替换时静默丢弃，无任何日志（server.rs:406-408）。
  • did_close 清空诊断时复用关闭前的版本号（server.rs:1904-1910 经 diagnostics.rs:657-660）。

WS-2 · 延迟与并发 高 依赖 WS-0

2.1 每次按键两次全项目分析

did_change 同时调度 schedule_diagnostics() 与 schedule_document_indexing()（server.rs:434-435）。二者分别走到：

  • collect_workspace_diagnostics_cancellable → clue::check_project_with_session，深度为 Check——最深的深度， 即 parse → HIR → scope graph → 类型检查 → 逃逸分析 → move/borrow 检查（diagnostics.rs:328-341、app/clue/src/lib.rs:985-1015）。
  • project_index_for_root_cancellable → clue::infer_project_with_session_cancellable，深度为 Infer（server.rs:1782-1833、index.rs:829-843）。

两者解析到同一个 Arc<Mutex<ProjectSession>>（session.rs:28-36），因此互相串行排队。 而会话缓存对每次按键都失效：load() 以 overlay 文本相等为前提短路（app/clue/src/lib.rs:700-712）， cached_analysis() 又要求 revision 相等（:729-738）， 而 overlay 每次按键都变 → revision 递增 → 缓存整体作废。真正被复用的只有 CheckSession 内部的 IncrementalParser/IncrementalTypeChecker（app/riddlec/src/pipeline.rs:418-424,1664-1667）， 即同一会话内的绿树复用，而非跨请求的 early cutoff。

目标与做法：

  1. 诊断深度懒惰化：改动后先发 parse/HIR/类型检查级诊断，把逃逸与 move/borrow 检查推迟到保存时或显式 pull。
  2. 索引不再按键触发：改为保存时 / 文件监听事件 / 显著更长的防抖；并直接复用诊断那一趟得到的 ProjectAnalysis，不要重跑 infer_project_*。
  3. 真正的 early cutoff：把分析缓存键从 revision 换成「每个包文件的内容哈希」， 使只改一个函数体不再作废整个 ProjectAnalysis（app/clue/src/lib.rs:675-680）。

2.2 五个处理器在异步执行器上跑重活

tower-lsp 在单个驱动任务内轮询处理器 future，因此这些调用会同时占满 4 个并发槽，拖慢所有请求而不只是自己：

处理器位置同步工作量
formattingserver.rs:461-486克隆文档 + format_source 全量重解析格式化 + 构建 LineIndex
folding_rangeserver.rs:488-499克隆文档 + 全文件解析

2.3 取消只停响应，不停 CPU

$/cancelRequest 确实被 tower-lsp 处理，但 abort 一个 future 只能在其下一个 await 点丢弃它， 无法停止已经在跑的 spawn_blocking 闭包。现有 RequestRevisions（server.rs:127-171） 是陈旧性判据而非取消信号，且只在流水线的阶段边界被查询（pipeline.rs:1599,1625,1639,1652,1668,1689,1695）， 已经越过阶段 6 的运行会把逃逸分析、move 检查与 MIR 降低做完。

做法：引入真正由客户端取消驱动的协作令牌——在 Cancellable 与路由器之间加一层 tower 层， 按 JSON-RPC id 把 AtomicBool 登记进共享表，把所有 *_cancellable 的谓词改为读该令牌， 并首先修掉 1.4 里 server.rs:559 那个硬编码的 || false。 没有这一步，其他所有优化都被「被取消却仍在跑」的并发浪费所压制。

2.4 快速止血（可独立合入）

  • --completion-delay-ms 默认值为 0（cli.rs:19-25,39），意味着 server.rs:849-854 的 sleep 被整段跳过，没有任何合并效果。改为 30–80 ms。
  • 诊断防抖是全局计数器 diagnostic_revision: AtomicU64（server.rs:94）， 在 A 文件输入会重置 B 文件待发诊断的计时。改为按 URI 分片的修订映射。
  • isIncomplete 在 ./:: 触发且列表非空时恒为 true（server.rs:912-919）， 但服务器每次都重算完整列表并给出精确 textEdit：客户端因此每键重新请求全项目分析，纯成本无收益。改回 false / 数组形式。

WS-4 · IDE 精度与大纲 高

  • 大纲丢失所有 impl 块：TopLevelItem::Impl(_) | TopLevelItem::Use(_) => None（editor_features.rs:215）， 于是 impl 里定义的方法不进文档符号/面包屑；但工作区符号包含它们（editor_features.rs:444,578-600）。 已核实的不对称：Ctrl+T 找得到方法，文件大纲找不到。
  • 范围精度错误：symbol() 把 range 与 selection_range 都设成名字跨度（editor_features.rs:285-293）， 层级条目同样（hierarchy.rs:223-224,236-237）、索引同样（index.rs:779）。 规范要求 range 是条目整体范围。这会影响大纲高亮、粘性滚动与 peek 视图。
  • 无未使用导入检测：全仓库没有这条诊断（只有 E0051「空 use 声明」，crates/scope-graph/src/builder.rs:869）； organize_import_edits 只做排序/去重/删空行（code_actions.rs:125-244）。
  • 语义 Token 漏注释：只映射了 SyntaxKind::LineComment（semantic_tokens.rs:769）， 而词法区分 DocComment/DocBlockComment/BlockComment（crates/syntax/src/lib.rs:72-84） ——文档注释与块注释完全没有高亮；且多行 token 被整体丢弃（semantic_tokens.rs:205-207,717-719）。

11 · 风险与缓解

风险影响缓解
性能结论未经实测——本规划全部延迟论断来自调用图推断，crate 内无 benchmark 与 tracing 可能把工程力气投在非瓶颈处 WS-0 先行；把实测数字作为 P2 内部排序的唯一依据；若实测显示 ProjectSession::load 而非流水线是瓶颈，则 2.1 的第 3 项（内容哈希）优先于第 1 项
诊断深度懒惰化会让 move/borrow 错误延迟出现 用户可能在保存前看不到借用错误 显式 textDocument/diagnostic pull 与保存事件仍跑全深度；在能力声明中保持 inter_file_dependencies: true 不变；把该行为写入 CHANGELOG 与文档
合并三个 ProjectSession 会让 completion 与 analysis 互相冲刷缓存 完成延迟反而变差 严格排在内容哈希键落地之后；先在埋点下验证两个变体命中同一哈希键的比例
positionEncoding 协商改动触及所有位置换算 可能引入新的偏移回归 先只加「客户端不支持 UTF-16 时明确报错」，把真正支持多编码作为独立后续；用含 emoji/中文注释的用例覆盖 LineIndex 与 offset_for_position
为 use 改写实现 willRenameFiles 需要编辑未打开文件 可能产生错误编辑或竞态 排在 P4 且独立评审；先实现「仅当被改名文件属于项目且所有受影响 use 都能静态确定」的子集，其余情况不发编辑
把冒烟测试接入 PR 门禁会增加 CI 时长 PR 反馈变慢 它已在夜间稳定运行；若超时，只在 ubuntu 单平台跑，并允许复用 debug 构建
